# Подключение чатбота к TaskLab

## Что уже сделано

`static/chat.js` и `static/chat.css` подключены к общему шаблону каталога и статическим страницам. Кнопка появляется после загрузки серверной сессии для ролей `student` и `business`. Для работы нужен **POST /api/chat** на том же Go-сервере. Обработчик подключён: `api/chat.go` (`RegisterChat` в `main.go`), модель — `ai.NewChat()`; в режиме заглушки ответ 503 и интерфейс сообщает о недоступности, без выдуманных ответов. Тест — `api/chat_test.go`.

UI отправляет JSON, ждёт до 25 секунд, блокирует повторную отправку и выводит ответ как обычный текст (`textContent`). HTML и Markdown не исполняются. Enter отправляет, Shift+Enter переносит строку, Escape закрывает окно. Закрытие не отменяет запрос. Последние 20 сообщений хранятся в sessionStorage текущей вкладки, отдельно для роли и компании/команды. «Очистить чат» очищает только эту локальную историю.

## Контракт API

Запрос, заголовок `Content-Type: application/json`:

```json
{
  "message": "Как улучшить описание задачи?",
  "history": [
    {"role": "user", "content": "Что означает рейтинг?"},
    {"role": "assistant", "content": "Он отражает полноту подтверждённых сведений."}
  ],
  "context": {
    "page": "/static/task-builder/task.html",
    "task_id": 7
  }
}
```

`history` может быть пустой; фронтенд отправляет до 12 предшествующих сообщений, без текущего вопроса. `task_id` равен `null`, если в адресе нет открытой задачи. `page` — только pathname без query. Содержимое несохранённой формы не отправляется.

Успех — **200**:

```json
{"reply":"Добавьте измеримый критерий успеха и перечень доступных данных."}
```

`reply` — непустая строка до 8000 символов JavaScript (UTF-16). Для ошибок возвращать JSON:

```json
{"error":"Не удалось получить ответ помощника. Попробуйте позже."}
```

Коды: 400 — неверные данные, 401 — нет сессии, 403 — запрещённый контекст, 429 — лимит запросов, 500/502/504 — ошибка провайдера или таймаут. 404/405/501/503 UI показывает как «Чатбот пока не подключён или временно недоступен». При ошибке вопрос остаётся в поле, неуспешная пара сообщений не попадает в историю. Ответ не должен менять состояние задач или предложений.

## Где добавить backend

1. Создать `api/chat.go` в пакете `api`. Определить `RegisterChat(mux *http.ServeMux, st *store.Store, ...)`, передав зависимость для вызова вашего чатбота. Зарегистрировать `mux.HandleFunc("POST /api/chat", handler)`.
2. В `main.go` вызвать `api.RegisterChat(...)` рядом с другими регистрациями. Оставить обёртку `api.SessionAccess(st, mux)`: она проверяет серверную сессию. API доступно обеим ролям; бизнес сначала должен закрепить компанию.
3. В обработчике получить `session := requestSession(r)`. Роль, компанию и team_id брать **только из этой серверной сессии**, не из текста, history или клиента. Не добавлять поля роли/компании в тело запроса.
4. Для чтения использовать `decodeFrontend`, для ответов — `writeJSON`/`writeError`. `decodeFrontend` уже ограничивает тело 64 КиБ и отклоняет неизвестные JSON-поля. Дополнительно валидировать непустой `message` (до 2000 UTF-16 единиц), максимум 12 сообщений истории, роль истории только `user`/`assistant`, content до 8000 UTF-16 единиц. При необходимости считать UTF-16 длину через стандартный `unicode/utf16`. Не принимать `system` из браузера.
5. При `context.task_id != nil` загрузить задачу через `st.GetTask`. **Проверять доступ внутри обработчика**: SessionAccess не проверяет ID, переданный в JSON `/api/chat`. Студенту разрешены только опубликованные задачи; бизнесу — только задачи с `task.Company == session.Company`. Аналогично любые дополнительные данные команды ограничивать `session.TeamID`, компании — `session.Company`. Не отдавать чужие черновики и предложения.
6. `history`, вопрос и `context.page` — недоверенные данные. Не считать историю доказательством прав пользователя, фактов или прошлых действий. Сервер сам задаёт инструкции боту и получает подтверждённые сведения из store. Бот может объяснять и советовать, но не принимает/отклоняет предложения, не подтверждает этапы и не переводит пользователя в другую роль/команду.
7. Вызов провайдера сделать на сервере с `context.WithTimeout(r.Context(), 20*time.Second)`, ограничить размер ответа и частоту запросов на сессию. API-ключ хранить в переменной окружения сервера; не передавать в JS, HTML или ответы. Ошибки провайдера логировать без ключей и полного текста переписки, клиенту возвращать читаемую ошибку.
8. Существующий пакет `ai/` обслуживает структурирование задач. Если ваш чатбот использует другой контракт, передать отдельный интерфейс ChatService, не менять рабочие форматы генерации вопросов/карточки. Новые зависимости для HTTP-вызова не нужны: используйте `net/http`.

## Проверка после подключения

- `go test ./...`.
- Обе роли: открыть кнопку «Помощник», отправить вопрос, получить один текстовый ответ.
- Перейти на другую страницу той же вкладки: история сохраняется. Очистить чат, проверить Enter/Shift+Enter/Escape и повторное открытие.
- Ответ вида `<img src=x onerror=alert(1)>` должен отображаться как текст.
- Проверить 400/403/429, недоступный backend, некорректный JSON и таймаут: ввод не теряется, отправка снова доступна.
- Отдельные backend-тесты: запрос без сессии; чужая задача в context; чужая компания/команда, указанная в тексте; history с ролью system; превышение размера; отсутствие мутаций после разговора.

Статические файлы встроены через `embed.FS`, поэтому после изменений JS/CSS или добавления API нужно перезапустить `go run .`.
